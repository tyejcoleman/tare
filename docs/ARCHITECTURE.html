rulecheck 0.2.0 · architecture

How it works

rulecheck reads the Claude Code session transcripts already sitting on your disk and reports, for every rule in your CLAUDE.md, whether the agent has ever actually reached the thing that rule governs.

~400 lines of Python stdlib only no network no model in the judging path

01

The question

A rule file is loaded into context on every single run. It costs tokens on every request, forever. Nobody has any idea which lines in it have ever mattered. rulecheck assigns each rule exactly one of three verdicts.

FIRED

The agent really did touch what this rule governs, in a recorded session.

Engagement, not compliance — see §08. It proves the agent was in the neighbourhood, not that it obeyed.

DORMANT

The rule is machine-observable, but no session has ever engaged it.

A dead letter. It pays rent in your context window on every run and has never once applied.

UNOBSERVABLE

The rule names nothing a machine can check — no path, no command, no identifier.

It may be excellent advice. It cannot be enforced or measured. In practice this is the largest bucket, and it is the finding, not a parser failure.

02

Two inputs, both already on disk

rulecheck introduces no new data collection. Everything it reads was written by tools you were already running.

InputWhereWhat is taken from it
Rule files CLAUDE.md, AGENTS.md,

The one non-obvious part

Claude Code stores a project's transcripts in a directory named after the project path, with every run of non-alphanumeric characters — slashes, spaces, dots, underscores — collapsed to a single dash. ~/Development/Hotel Portal becomes -Users-you-Development-Hotel-Portal. Getting this wrong is silent: you find no transcripts and conclude the repo has no history. rulecheck slugifies the same way, then falls back to a suffix match for older encodings.

03

The pipeline

Five stages, all deterministic. Nothing is inferred, nothing is generated, and the same inputs always produce a byte-identical report.

01

Extract candidate rules

rule file → list of normative statements

Markdown is walked line by line. Fenced code blocks, tables, HTML and images are skipped. A line becomes a candidate if it is a list item, a bolded directive, or a sentence in a prose paragraph.

Prose files need care: hard-wrapped markdown splits one sentence across several lines, so paragraphs are buffered and split on sentence boundaries as a single string. Without that, every rule comes out as a fragment.

02

Keep the ones that are actually rules

candidates → rules

A candidate survives if it carries a modal verb — must, never, always, do not, forbidden, required, should, avoid, ensure — or if it is a named directive, meaning it leads with bold text. That second test matters: a line like **No service-role key in the client** is unmistakably a rule and contains no modal verb at all.

Length is bounded to 25–400 characters, and duplicates are collapsed on the first 90 characters of lowercased text.

03

Pull out the machine-checkable anchors

rule text → set of literals

This stage decides everything downstream. Three patterns are harvested:

# backticked identifiers — but not backticked prose
BACKTICK  `([^`\n]{2,80})`        → rejected if it is plain words
PATHISH   src/db/client.ts, migrations/003.sql, hooks.json
CMDISH    npm run build, git push, docker compose up

A rule with no literals is UNOBSERVABLE and stops here. It is never counted as dormant, because "we cannot check this" and "this never happened" are different claims and conflating them would be a lie.

04

Flatten the transcripts into evidence

*.jsonl → one lowercased text blob per session

Each line is scanned for "tool_use" before being parsed at all — the cheap substring test skips the overwhelming majority of lines in a large transcript. Surviving lines are parsed as JSON, filtered to assistant turns, and every tool_use block's input is flattened across the fields that carry real subjects:

file_path · path · command · pattern · notebook_path
url · old_string · new_string · content · prompt · query

Transcripts over 60 MB are skipped rather than risk stalling on a pathological file.

05

Match, and count the evidence

literals × sessions → verdict

A rule fires in a session if any one of its literals appears anywhere in that session's evidence blob. Fired in at least one session ⇒ FIRED. Fired in none ⇒ DORMANT. Every verdict is auditable with --rule N, which prints the exact literals that matched and the sessions they matched in.

04

The verdict, exhaustively

The entire decision is a two-question truth table. There is no scoring, no threshold, and no ranking model.

Has literals?Matched a session?VerdictWhat it means for you
no— UNOBSERVABLE Rewrite it to name a path, command or identifier, or accept that it is advice rather than policy.
yesno DORMANT Delete it, or find out why nobody ever goes near the code it governs.
yesyes FIRED It is load-bearing. Worth the context it costs.
The low-evidence guard

Under 150 recorded tool calls in a repo, rulecheck refuses to report a dead-letter percentage and says so on the report. "This rule never fired" and "we barely looked" are different statements, and a confident wrong number is worse than no number. The uncheckable share is still reported, because it does not depend on how much activity there has been.

05

The accruing record

A one-shot run can only see the transcripts still on disk. So it can tell you "this rule has never fired" — but never "this rule stopped firing five weeks ago." The second sentence is the useful one, and it needs a record that outlives its source.

The plugin installs a single SessionEnd hook. At the end of each session it reads that one transcript, applies the same matching logic, and appends one line to ~/.rulecheck/history.jsonl: 

{"ts": "2026-07-27T02:55:50+00:00", "session": "493435eb",
 "repo": "/Users/you/Development/Hotel Portal",
 "rules": 20, "checkable": 16, "tool_calls": 237,
 "fired": ["41c9da1956", "755174349f", "c5464646a9"]}

Those identifiers are hashes of the rule text, not positions in the file. Edit line 4 and the rule on line 40 keeps its entire track record. Reword a rule and it correctly reads as a new rule with no history — which is the honest answer, because it is now a different rule.

--history then reports what a single run cannot: which rules have never fired across the whole recorded window, and when each of the others was last seen.

The hook can never break your session

Every failure path exits 0 silently — unparseable stdin, a missing transcript, a repo with no rule file, an unwritable home directory. It has a 15-second timeout and takes no action other than appending one line. A measurement tool that can break your editor is not worth having.

06

What it deliberately will not do

These are constraints, not missing features. Each one is load-bearing.

  • No model in the judging path. Every verdict is literal matching, so the same input always gives the same answer, nothing is invented, and any verdict can be audited line by line. An earlier prototype put a model in exactly this seat — asking it to judge whether an action conflicted with a recorded decision — and it scored AUC 0.465, below chance. Any future component that asks a model to adjudicate has to pass that same kill test first.
  • No network, no account, no telemetry. The single file it writes is the local history log. Delete it and you lose the history and nothing else.
  • No writes to your repo. rulecheck will tell you a rule is dead. Deleting it is your call — editing someone's CLAUDE.md is not a thing a measurement tool should do.
  • No dead-letter rate on thin evidence. See §04.

08

Limits — read before trusting a number

  • FIRED is engagement, not compliance. It means the rule's literals appeared in a session's tool inputs. The agent was in the neighbourhood. It does not prove the rule was obeyed, and it should never be described as "followed". Closing that gap is the hard, unsolved part.
  • Prose rules land in UNOBSERVABLE by construction. That is the measurement working, not the parser failing — but it does mean the count is a floor on how much of your rule file is unenforceable, not a judgement on its quality.
  • Rule extraction is heuristic. It reads list items, bolded directives and normative sentences. It will miss some rules and over-collect others. --json shows you exactly what it found so you can check.
  • Claude Code transcripts only. Cursor and Codex are the obvious next adapters; the matching stage is format-agnostic and would not change.
